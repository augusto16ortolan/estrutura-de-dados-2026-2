Estrutura de Dados - Trabalho em grupo

Como trabalhar simultaneamente no GitHub

Tutorial para grupos de ate 7 alunos criarem branches, fazerem commits, abrirem Pull Requests, revisarem codigo e entregarem um repositorio publico com participacao real de todos.

1. Visao geral do fluxo

O grupo deve evitar trabalhar diretamente na branch principal. Cada aluno cria sua propria branch, faz commits, envia para o GitHub e abre um Pull Request para juntar o codigo ao projeto.

main-> branch do aluno-> commit-> push-> Pull Request-> review-> merge
Regra do trabalho: todos os integrantes precisam fazer commits reais no repositorio. Nao vale apenas um aluno subir tudo pelo grupo.

2. Conceitos essenciais

Termo Significado
Repositorio remoto Projeto hospedado no GitHub, acessivel para o grupo e para o professor.
Clone local Copia do projeto no computador de cada aluno.
Branch Linha separada de trabalho para mexer no codigo sem baguncar a main.
Commit Registro de uma alteracao feita por um aluno.
Push Envio dos commits locais para o GitHub.
Pull Request Pedido para revisar e juntar uma branch na main.
Merge Ato de juntar uma branch aprovada na branch principal.
Conflito Acontece quando duas pessoas alteram a mesma parte do mesmo arquivo.

3. Glossario rapido

Use estas frases curtas quando bater duvida durante o trabalho.

Commit

Um ponto salvo na historia do projeto. Mostra o que mudou e quem mudou.

Push

Enviar seus commits do computador para o GitHub.

Pull

Baixar para seu computador as novidades que estao no GitHub.

Branch

Uma linha separada de trabalho para desenvolver sem mexer direto na main.

Pull Request

Pedido para revisar e juntar sua branch na branch principal.

Conflito

Quando duas alteracoes mexem no mesmo trecho e o Git precisa de decisao humana.

4. Criar e configurar o repositorio publico

  1. Um integrante cria o repositorio no GitHub.
  2. O repositorio deve ficar como Public.
  3. O nome pode seguir o formato estoque-vendas-estrutura-dados.
  4. Adicione um README.md inicial.
  5. Convide os demais integrantes em Settings -> Collaborators.
Use um unico repositorio por grupo. Todos trabalham nele e aparecem no historico de commits.

5. Primeiro dia do grupo

Antes de dividir tarefas grandes, o grupo deve garantir que todos conseguem acessar o repositorio, clonar, criar branch e fazer push.

criar repositorio publico-> convidar colegas-> aceitar convite-> clonar-> configurar Git-> push de teste
  1. Um integrante cria o repositorio publico no GitHub.
  2. Esse integrante adiciona todos os colegas como colaboradores.
  3. Cada colega aceita o convite pelo GitHub ou pelo e-mail.
  4. Cada aluno clona o repositorio no proprio computador.
  5. Cada aluno confere nome e e-mail do Git.
  6. Cada aluno cria uma branch de teste e faz um commit simples.
Teste de push no primeiro dia 
git config --global --list
git checkout main
git pull origin main
git checkout -b teste/nome-aluno
git status
git push origin teste/nome-aluno
Resultado esperado: cada aluno consegue enviar uma branch propria para o GitHub. Isso evita descobrir problema de acesso no dia da entrega.

6. Configuracao inicial do Git

Cada aluno deve configurar nome e e-mail no proprio computador.

Configurar nome e e-mail 
git config --global user.name "Seu Nome"
git config --global user.email "seu-email@exemplo.com"
git config --global --list

Depois, cada aluno clona o repositorio do grupo:

Clonar repositorio 
git clone https://github.com/usuario/repositorio-do-grupo.git
cd repositorio-do-grupo

7. Criar uma branch individual

Antes de alterar codigo, crie uma branch com seu nome e a funcionalidade. Isso ajuda o grupo a saber quem esta mexendo em cada parte.

Criar branch 
git checkout main
git pull origin main
git checkout -b feature/nome-aluno-clientes

Padrao recomendado

  • feature/nome-aluno-clientes
  • feature/nome-aluno-produtos
  • feature/nome-aluno-vendas
  • fix/nome-aluno-correcao-menu

8. Rotina diaria de trabalho

Antes de programar, atualize sua copia local. Depois trabalhe na sua branch.

git pull-> criar branch-> alterar arquivos-> testar-> commit-> push-> PR
Verificar estado do projeto 
git status
Evite alterar tudo de uma vez. Commits pequenos sao mais faceis de revisar e ajudam a provar a participacao de cada integrante.

9. Exemplos de fluxo

Os exemplos abaixo mostram situacoes comuns em um trabalho em grupo. A regra principal se repete em todos: cada aluno trabalha em uma branch propria, faz seus commits e abre Pull Request.

Fluxo 1: Ana implementa clientes

Ana ficou responsavel por implementar cadastro, busca e listagem de clientes usando a LSE. Ela cria uma branch propria, faz commits pequenos e abre um PR.

main-> feature/ana-clientes-lse-> commits da Ana-> push-> PR-> review-> merge
Fluxo individual completo 
git checkout main
git pull origin main
git checkout -b feature/ana-clientes-lse
git status
git add .
git commit -m "feat: implementar cadastro de clientes"
git push origin feature/ana-clientes-lse
Resultado esperado: no GitHub aparece uma branch da Ana com commits proprios e um Pull Request pronto para revisao.
Erro comum: fazer tudo em um unico commit grande. Prefira commits menores, como cadastro, busca e listagem em etapas separadas.

Fluxo 2: dois alunos trabalham ao mesmo tempo

Ana trabalha em clientes/LSE enquanto Bruno trabalha em produtos/LDE. Os dois podem trabalhar ao mesmo tempo porque usam branches diferentes.

main-> feature/ana-clientes-lse-> PR clientes+ feature/bruno-produtos-lde-> PR produtos
Ana: clientes 
git checkout main
git pull origin main
git checkout -b feature/ana-clientes-lse
git add .
git commit -m "feat: implementar lse de clientes"
git push origin feature/ana-clientes-lse
Bruno: produtos 
git checkout main
git pull origin main
git checkout -b feature/bruno-produtos-lde
git add .
git commit -m "feat: implementar lde de produtos"
git push origin feature/bruno-produtos-lde
Resultado esperado: o GitHub mostra dois Pull Requests separados, cada um com o historico de quem trabalhou naquela parte.
Erro comum: os dois alterarem o mesmo arquivo sem combinar. Se precisarem mexer em `main.py` ou `README.md`, conversem antes.

Fluxo 3: atualizar branch depois que outro PR foi mergeado

Bruno ainda esta trabalhando em produtos, mas o PR de Ana ja foi mergeado na `main`. Bruno deve trazer as novidades da `main` para sua branch antes de continuar.

PR da Ana mergeado-> Bruno atualiza main-> volta para sua branch-> git merge main-> continua trabalho
Atualizar branch com main recente 
git checkout main
git pull origin main
git checkout feature/bruno-produtos-lde
git merge main
Resultado esperado: a branch de Bruno passa a conter tambem as alteracoes que Ana ja juntou na `main`.
Erro comum: abrir PR com a branch muito desatualizada. Isso aumenta a chance de conflitos e dificulta a revisao.

Fluxo 4: conflito simples no README ou main.py

Ana e Bruno alteraram a mesma linha do `README.md` ou do `main.py`. O Git nao sabe qual versao manter e marca um conflito para o grupo resolver manualmente.

duas alteracoes no mesmo trecho-> Git marca conflito-> grupo conversa-> edita arquivo-> commit de resolucao-> push
Ver conflito e finalizar resolucao 
git status
# abrir o arquivo com conflito e editar manualmente
git add .
git commit -m "fix: resolver conflito"
git push origin feature/nome-da-branch
Resultado esperado: o Pull Request volta a ficar sem conflito e pode ser revisado pelo grupo.
Erro comum: apagar a parte do colega sem entender. Em conflito, conversem e deixem no arquivo a versao correta para o projeto.

10. Commit e push

Depois de alterar e testar, registre suas mudancas com commit.

Adicionar e commitar 
git status
git add .
git commit -m "feat: cadastrar clientes"
Enviar branch para o GitHub 
git push origin feature/nome-aluno-clientes

Mensagens de commit

  • feat: cadastrar clientes
  • fix: corrigir validacao de estoque
  • docs: atualizar README
  • refactor: reorganizar service

11. Como provar participacao

A participacao aparece no GitHub quando cada integrante faz commits com seu proprio usuario, nome e e-mail configurados corretamente.

Onde conferir

Abra o repositorio no GitHub e veja a aba de commits ou acesse Insights -> Contributors.

Cuidado

Se um aluno commitar no computador de outro, o commit pode aparecer com nome/e-mail errado.

Conferir autor dos commits 
git config --global --list
git log --oneline --decorate
  • Cada integrante deve ter commits no historico.
  • Cada commit deve representar uma alteracao real no projeto.
  • O grupo deve evitar que uma unica pessoa suba tudo no final.

12. Abrir Pull Request

  1. Entre no repositorio do grupo no GitHub.
  2. Clique em Compare & pull request.
  3. Confira se a branch de origem e a sua branch.
  4. Confira se o destino e main.
  5. Escreva um titulo claro e explique o que foi feito.
  6. Peça para pelo menos um colega revisar.
Um bom PR explica o que mudou, quais arquivos principais foram alterados e como testar.

13. Modelo de Pull Request

Copie este modelo para descrever melhor o PR no GitHub.

Modelo de descricao de PR 
Titulo: feat: implementar cadastro de produtos

O que foi feito:
- Criei a classe Produto
- Implementei cadastro no menu
- Salvei produtos no CSV

Arquivos principais:
- models/produto.py
- services/estoque_service.py
- data/produtos.csv

Como testar:
- Rodar python3 main.py
- Escolher a opcao 5
- Cadastrar um produto
- Listar produtos na opcao 6

Observacoes para o revisor:
- Conferir se o ID esta sequencial
- Conferir se preco negativo e bloqueado
Um PR bem explicado facilita a revisao e mostra que o aluno entende o que alterou.

14. Review e merge

O grupo deve revisar antes de juntar na main. A revisao evita que uma parte quebre outra.

  1. Leia os arquivos alterados no Pull Request.
  2. Comente se encontrar erro ou duvida.
  3. Rode o projeto localmente quando possivel.
  4. Depois da aprovacao, clique em Merge pull request.
  5. Apague a branch remota se o GitHub oferecer essa opcao.
Nao faca merge de codigo que nao roda ou que ninguem entendeu. O grupo inteiro precisa conseguir explicar a entrega.

15. Atualizar o projeto local depois do merge

Quando alguem faz merge, todos devem atualizar a copia local.

Atualizar main local 
git checkout main
git pull origin main

Se for continuar trabalhando, crie outra branch a partir da main atualizada.

16. Comandos seguros de apoio

Estes comandos ajudam a se localizar no projeto sem alterar o historico do Git. Use sempre que estiver em duvida.

Ver estado e branches 
git status
git branch
Ver historico curto 
git log --oneline
Trocar de branch 
git checkout nome-da-branch
Restaurar arquivo com cuidado 
git restore nome-do-arquivo
Cuidado com git restore: ele descarta alteracoes locais daquele arquivo. Use apenas quando tiver certeza de que pode perder essas alteracoes.

17. Resolver conflitos basicos

Conflito acontece quando o Git nao consegue decidir sozinho qual versao manter. Normalmente aparece quando duas pessoas mexem no mesmo trecho do mesmo arquivo.

Trazer main para sua branch 
git checkout feature/nome-aluno-clientes
git pull origin main

Se aparecer conflito:

  1. Abra o arquivo indicado pelo Git.
  2. Procure marcas como <<<<<<<, ======= e >>>>>>>.
  3. Converse com quem alterou a outra parte.
  4. Edite o arquivo deixando a versao correta.
  5. Salve, teste e finalize o commit.
Finalizar conflito resolvido 
git status
git add .
git commit -m "fix: resolver conflito"
git push origin feature/nome-aluno-clientes

18. Erros comuns e como resolver

Problema Como agir
Fiz commit direto na main Avise o grupo, faca push apenas se todos concordarem e volte a usar branches nos proximos commits.
Esqueci de fazer git pull Atualize a branch antes de abrir PR e resolva conflitos se aparecerem.
O push foi rejeitado Alguem enviou mudancas antes. Baixe as novidades e envie novamente.
Mensagem de commit ficou ruim Nos proximos commits, use mensagens claras como feat: implementar fila de vendas.
Alterei arquivo errado Confira com git status. Se ainda nao commitou, restaure com cuidado.
Conflito com codigo do colega Conversem, decidam a versao correta, editem o arquivo e facam commit da resolucao.
Quando o push for rejeitado 
git pull origin nome-da-sua-branch
git push origin nome-da-sua-branch
Evite comandos destrutivos quando estiver em duvida. Antes de apagar ou restaurar arquivos, converse com o grupo.

21. Fluxo recomendado de integracao

Nem toda parte do trabalho deve ser mergeada em qualquer ordem. Um caminho simples reduz conflitos e facilita os testes.

modelos-> clientes/produtos-> vendas-> desfazer-> relatorios-> README/testes
  1. Integre primeiro classes base e estruturas.
  2. Depois integre clientes e produtos.
  3. Em seguida, implemente vendas e fila.
  4. Depois complete pilha e desfazer.
  5. Finalize relatorios, README e testes manuais.

22. Nao facam isso

  • Nao deixem para subir tudo no ultimo dia.
  • Nao trabalhem todos diretamente na main.
  • Nao apaguem codigo do colega sem conversar.
  • Nao misturem varias funcionalidades sem relacao no mesmo commit.
  • Nao deixem integrante sem commit proprio.
  • Nao copiem projeto de outro grupo.
  • Nao facam merge de codigo que ninguem testou.
